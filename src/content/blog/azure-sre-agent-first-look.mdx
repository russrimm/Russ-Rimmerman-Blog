Azure SRE Agent is Microsoft's operations agent for the work that eats an
on-call rotation: triaging incidents, checking whether services are actually
healthy, and running the runbook nobody has updated since the last reorg. It
went generally available in March 2026, and if you haven't tried it yet, the
short version is that it does the first twenty minutes of an investigation for
you and shows its work.

I gave it an hour. In that hour it reviewed one of my repos and handed back
findings that went well past the usual security scan into performance,
accessibility, and UX. Then I asked it what my Application Insights instances
were actually recording, and it surfaced unhealthy telemetry from Dataverse,
Copilot Studio, a couple of app servers, and a Foundry agent in a single pass.

Here's what it is, what it can do, and where I'd be careful with it.

## What Azure SRE Agent is

It connects your observability tools, incident platforms, and source
repositories into one workflow. Instead of hopping between a dashboard,
PagerDuty, and Slack when something breaks, you get a single investigation with
the "what changed, what's affected, what to do next" already worked out.

<Screenshot
  src={operationsHub}
  alt="Azure SRE Agent Operations Hub overview showing a setup checklist with Code, Logs, and Azure resources connected, a daily volume by source chart, an empty pending actions panel, and a system health panel reporting a healthy agent process and two healthy connectors"
  caption="The Operations Hub is the front door: what's connected, what's pending your approval, and whether the agent itself is healthy."
/>

It ships with six built-in subagents — Explore, Plan, CodeReview, Bash,
Verification, and GeneralPurpose — plus extension points for custom skills,
Python tools, MCP server connections, and event-triggered hooks. Microsoft has
since added native Application Insights and Log Analytics connectors that
handle the RBAC wiring for you, so telemetry is queryable the moment you
connect a resource instead of after a separate permissions project.

Those hooks aren't something you script yourself. The Automation blade takes
two kinds of trigger: a scheduled task that runs a check on a cadence you set,
or an HTTP trigger you point an alert rule or webhook at, so an Azure Monitor
alert can start the investigation before anyone opens a laptop.

<Screenshot
  src={automation}
  alt="Azure SRE Agent Automation blade with the Create menu expanded, showing the two options: Scheduled task and HTTP trigger"
  caption="Automation gives you two entry points — a scheduled check or an HTTP trigger fired by an alert or webhook."
/>

Nothing it proposes deploys without a human approving it first. That
distinction matters more than it sounds like it should: this is an agent that
recommends and drafts, not one that reboots your production database because
it decided that was a good idea at 3 a.m. Microsoft's own writeup on the
rollout describes the mechanics behind that guardrail: the agent explains what
it intends to do and why before acting, every interaction produces a full
audit trail, routine operations run autonomously, and anything flagged as
high-impact pauses for in-workflow sign-off. If your environment uses VNet
integration, that traffic still routes through your own network, so your NSG
rules, private DNS, and firewalls apply the same way they would to a human
making the change. See
[Rethinking cloud operations with Azure SRE Agent](https://techcommunity.microsoft.com/blog/appsonazureblog/a-paradigm-shift-in-cloud-operations-with-azure-sre-agent/4533244)
for the full picture.

You set that approval model before anything runs. When you wire up a
connector, every tool it exposes gets its own permission: Allow lets the agent
call it unattended, Ask forces a prompt each time. The Microsoft Teams
connector I set up exposes 71 tools, and they're individually switchable
rather than a single all-or-nothing grant. If you're rolling this out to a
team, that page is where you decide what the agent can do on its own and what
it has to ask about.

<Screenshot
  src={toolPermissions}
  alt="Azure SRE Agent connector setup wizard on the Configure tools step, showing 71 of 71 tools selected with a per-tool parameter policy toggle and an Allow or Ask permission control for each one"
  caption="Per-tool permissions during connector setup — Allow for unattended calls, Ask to force a prompt."
/>

Those extension points aren't purely theoretical. Microsoft added a plugin
marketplace so you're not building every skill from zero: it lets you browse
and install community and internal skills and MCP integrations from
GitHub-hosted repositories, including private repos and GitHub Enterprise.
Worth knowing before you go looking for it: a new agent has no marketplace
registered at all, and the Plugins blade sits empty until you add one. The
Add marketplace dialog offers two well-known ones as presets: Azure's own
[Azure SRE Agent Plugins](https://github.com/Azure/sre-agent-plugins) and
Anthropic's [Claude Plugins](https://github.com/anthropics/claude-plugins-official).
You can also point it at any other repo by `owner/repo`, a github.com URL,
or a `tenant.ghe.com` URL. Every install is pinned to a specific git commit,
so an upstream change to a skill you installed months ago doesn't quietly
alter your agent's behavior until you choose to update it.

<Screenshot
  src={pluginsMarketplace}
  alt="Add marketplace or plugin dialog in Azure SRE Agent with the well-known marketplaces dropdown open, showing two options: Azure SRE Agent Plugins (Azure/sre-agent-plugins) and Claude Plugins (anthropics/claude-plugins-official), above a field for a marketplace URL or owner/repo"
  caption="Nothing is registered by default. The two well-known marketplaces are presets you pick, not defaults you inherit."
/>


One thing worth flagging if you're the one managing this for a team: private
marketplaces store a single credential — an OAuth token, a personal access
token, or a GitHub App — at the marketplace level, and every install from
that marketplace uses it. SRE Agent checks that the stored credential can
read the repo, not that the person installing the plugin personally has
access to it. Anyone with the Author or Administrator role on the agent can
install from any registered marketplace, regardless of their own GitHub
permissions. If you need to lock that down, the control point is the agent's
RBAC roles, not GitHub repo access.

## What setup actually looks like

An agent is an Azure resource, so it starts where every Azure resource
starts: a subscription, a resource group, and a region. You create it from
the agent list at [sre.azure.com](https://sre.azure.com), and once it exists
it shows up alongside any others you have, region and all. Mine live in two
different regions because I built them at different times and never went
back to tidy that up.

<Screenshot
  src={quickstartAgentList}
  alt="Azure SRE Agent portal agent list showing two agents named sre-doc and the-sre-fixer with their subscription blurred, resource group appinsights, and regions North Central US and East US 2, above a Create agent button"
  caption="The agent list. Each one is a real Azure resource in a subscription, resource group, and region."
/>

Open a new agent and it tells you what it still needs. The setup strip runs
across the top of the chat and tracks five things: Incidents, Knowledge
files, Code, Logs, and Azure resources. Green check means connected, hollow
circle means the agent is flying without it. You don't have to finish all
five before asking a question. I ran useful investigations with Incidents
and Knowledge files still unconfigured. But the strip is honest about what
it can't see yet.

<Screenshot
  src={quickstartSetup}
  alt="Azure SRE Agent setup checklist expanded, showing Incidents and Knowledge files as not configured, and Code with one repository, Logs with one log provider, and Azure resources with one Azure resource all marked configured"
  caption="The setup strip, expanded. Two unconfigured, three connected, and it works fine with the three."
/>

Code Access is where the repo connection lives, and it's per-domain rather
than per-repo: you authorize github.com or your GitHub Enterprise host once,
then add repositories under it. GitHub, Azure DevOps, and GitLab each get
their own tab. Once a repo syncs, you get a Ready status and a timestamp, so
you can tell at a glance whether the agent is reviewing today's code or a
snapshot from last week.

<Screenshot
  src={quickstartCodeAccess}
  alt="Code Access Configuration page in Azure SRE Agent with tabs for GitHub, Azure DevOps, and GitLab, showing a connected github.com domain using OAuth and one repository named PortalofPortals with a Ready status and a sync timestamp"
  caption="Code Access. Authorize the domain once, then add repos under it. The sync time tells you how fresh the review is."
/>

The permissions story goes deeper than the per-connector toggles. The Tools
blade lists every built-in tool the agent can call. Fifty of them on my
agent, 35 active, and each one has both an on/off switch and an
Allow-or-Ask permission. A few are locked on and can't be disabled. They're
grouped by category, so you can reason about them in batches instead of one
at a time: System, DevOps, Workspace Operation, and so on. There are
separate tabs for MCP servers, custom tools, advanced permissions, and
approval expiration.

<Screenshot
  src={builtinTools}
  alt="Tools page in Azure SRE Agent showing 35 of 50 active built-in tools in a table with On/Off toggles, Allow or Ask permission controls, category, and description columns, plus tabs for MCP servers and services, custom tools, advanced permissions, and approval expiration"
  caption="Every built-in tool, individually switchable, each with its own Allow or Ask setting. Some are locked on."
/>

If you're rolling this out to a team, this page and the connector one are
where the actual policy lives. Everything else is configuration; these two
decide what the agent is allowed to do when nobody's watching.

## The code review went further than I expected

I pointed the CodeReview subagent at one of my project repos expecting the
usual: dependency CVEs, a couple of hardcoded secrets I'd meant to rotate out,
maybe an injection risk in a query I'd written too quickly. I got that. What
I didn't expect was the rest of the list.

<Screenshot
  src={codeReviewThread}
  alt="Azure SRE Agent chat thread titled portalofportals repository code recommendations, showing a parallel exploration step with two completed subagents, Review and Explore, followed by recommendations ordered by severity"
  caption="One question, one thread. The agent picks its own subagents and shows each step as it runs."
/>

Before it answered, it fanned out. A CodeReview subagent took the security and
convention pass while an Explore subagent mapped the repo structure, both
running at once, both reporting back before the agent synthesized anything.
That structure is visible in the thread rather than hidden behind a spinner,
which matters when you want to know whether a finding came from reading the
code or from guessing at it.

<Screenshot
  src={parallelExploration}
  alt="Expanded parallel exploration card in Azure SRE Agent showing final results from two subagents side by side: a CodeReview agent summarizing a full repository review of a Next.js and React application, and an Explore agent reporting 813 route files across the API tree"
  caption="Both subagents' final results, side by side — including the Explore agent counting 813 route files."
/>

It flagged a performance issue in how I was paginating a large result set,
an accessibility gap where a custom form control had no accessible label, and
a UX inconsistency between two error messages that told users two different
things for the same failure. None of that is exotic advice on its own — any
good reviewer would catch it. What stood out was getting security, performance,
accessibility, and UX findings back in the same pass, against my own code, in
minutes instead of a scheduled review cycle.

The findings came back ordered by severity, each one pointing at the specific
file and line rather than describing the problem in the abstract. A pre-release
`next-auth` sitting under 800-plus API routes, unguarded `console.log` calls
leaking partial API keys and decoded token claims into production logs,
hardcoded hex colors in six chart components that bypassed the theme tokens
already defined in `globals.css`. Every one of those was checkable in under a
minute because it told me where to look.

<Screenshot
  src={codeReviewFindings}
  alt="Azure SRE Agent code recommendations listing a pre-release next-auth dependency, unguarded console.log calls in API routes leaking partial API keys and decoded token claims, and a table of six chart components with hardcoded hex colors that bypass the theme system"
  caption="Findings with file paths and a suggested fix attached — not a generic 'consider reviewing your logging' note."
/>

If you run a solo shop or a small team without a dedicated accessibility or
performance reviewer, that's the gap this fills. Not a replacement for a real
code review culture, but a much earlier catch than "we'll get to it before
launch."

## Then it checked what my telemetry was actually saying

The second half of the hour was the one that changed how I think about this
tool. I have Application Insights wired up across several different pieces of
my environment: Dataverse, a Copilot Studio agent, a couple of app servers,
and a Foundry-hosted agent. Each of those emits its own telemetry, and
normally checking all of it means opening separate blades, running separate
KQL queries, and manually correlating anything that looks off.

Once Azure SRE Agent had read access to those Application Insights resources,
it queried requests, dependencies, and exceptions across all of them and
called out the unhealthy signals directly: a latency trend on one app server
that had been quietly climbing, an elevated exception rate coming out of the
Copilot Studio agent, and a dependency call from the Foundry agent that was
failing more often than it should. It correlated pieces of that with recent
changes and proposed what to look at first, rather than handing me four
dashboards and telling me to figure it out myself.

That's the difference between monitoring and triage. Monitoring tells you
something is happening. Triage tells you what to do about it, and where to
start.

## One prompt, one health check

Since writing the first version of this post I went back and gave the agent
a deliberately lazy prompt, the kind you'd actually type at 2 a.m.: give me
a health check across everything you're connected to, list the Azure
resources you manage, query Application Insights for the last 24 hours, and
tell me what looks unhealthy and what you'd investigate first.

It took 147 seconds. The interesting part is what it showed while it worked.
It announced it was gathering everything in parallel, then ran the actual
commands in the open: `az graph query` calls against Resource Graph, KQL
against the requests, exceptions, and dependencies tables in Application
Insights, with each one labeled and each one marked complete as it landed.
The Resource Graph calls carried a **Medium risk** tag. You can read the
exact query it ran and copy it out.

<Screenshot
  src={demoRunning}
  alt="Azure SRE Agent thread mid-investigation showing a step labeled Performing comprehensive system health diagnostics, several completed Monitor Resource Log Query steps, and two Executing graph query cards tagged Medium risk with the raw az graph query commands visible"
  caption="Mid-run. The queries aren't summarized for you. They're printed, tagged with a risk level, and copyable."
/>

The answer opened with an inventory, then a section headed "What's Unhealthy
/ Noteworthy." All 13 VMs deallocated, including a 10-node compute fleet.
Seven of ten web apps stopped, two of which still had failure-anomaly alert
rules pointed at them, which, as it noted, is an odd combination if
they're meant to be off.

<Screenshot
  src={demoFindings}
  alt="Azure SRE Agent health check results listing resource inventory counts, then findings that all 13 VMs are deallocated, that 7 of 10 web apps are stopped with running and stopped apps in a table, and that one Application Insights resource shows a 100 percent request failure rate marked benign"
  caption="Inventory first, then what's actually wrong, including the stopped apps that still have alert rules pointed at them."
/>

The finding I keep coming back to is the third one. One Application Insights
resource showed a 100 percent request failure rate over 24 hours, which
looks alarming until you read the next line: four requests, all 404s, all
for `GET /robots933456.txt`. That's the App Service internal health probe
hitting a container. The agent labeled it benign, explained why, and then
made the point that actually mattered: near-zero real traffic means either
nobody is using the app or the SDK isn't wired up correctly.

A dashboard would have drawn that as a red 100 percent and left me to work
out the rest. Catching a false positive and then finding the real problem
hiding behind it is the part that's hard to automate, and it's the part it
did well.

It closed with a priority table, P1 through P4, each row carrying a reason
rather than just a severity, and a separate list of what looked healthy so I
wasn't left guessing about the things it didn't mention.

<Screenshot
  src={demoPriority}
  alt="Azure SRE Agent investigation priority table with rows P1 through P4 listing the issue and the reason for its priority, followed by a What Looks Healthy list naming running web apps with their pricing tiers, enabled logic apps, provisioned Cosmos DB accounts, key vaults, and API Management instances"
  caption="P1 through P4 with reasoning attached, plus an explicit healthy list so silence doesn't get mistaken for a pass."
/>

Its closing line was the right one: investigate the telemetry gap first,
because it couldn't tell me whether my main app was healthy when there was
no signal coming out of it. That's a better answer than a fake all-clear.

## The parts I didn't expect to use

A few blades I ignored on the first pass turned out to be the ones I'd
actually keep.

**Live Reports** are dashboards you build by talking to the agent. You
describe what you want, it authors the report, and the report re-queries
live data every time you open it. Each one is versioned and keeps a link
back to the thread that created it, so when the numbers look wrong you can
go read how they were defined instead of reverse-engineering a chart.

<Screenshot
  src={liveReport}
  alt="A live report in Azure SRE Agent titled MCViewer Metrics Dashboard showing KPI tiles for total requests, failed requests, and average duration over 24 hours, above line and bar charts for request count, average request duration, failed requests, and dependency count"
  caption="A dashboard authored by chatting with the agent, versioned, with an Open authoring thread button so you can see how it was built."
/>

**Incidents** is the piece I still haven't connected, and the portal is
blunt about what that costs you: without an incident platform wired up, the
agent handles conversations and scheduled work but doesn't have a queue to
work from. The same blade carries triggers and response plans, which is
where the "respond automatically when this fires" behavior gets defined.

<Screenshot
  src={incidentsOnboarding}
  alt="Incidents page in Azure SRE Agent with tabs for Incidents and Triggers plus response plans, agent status counters for pending user input, in progress, and completed all at zero, and a get started panel prompting to connect an incident platform"
  caption="Incidents, unconnected. The counters and the response-plan tab only start earning their keep once a platform is wired in."
/>

**Agent Canvas** is where the subagent story stops being something Microsoft
does for you and starts being something you build. You can create your own
subagents and skills, wire tools to them, view the whole thing as a graph or
a table, and test it in a playground before it touches anything real.

## What the hour actually cost

Worth knowing before you turn this on: billing runs on Azure agent units, or
AAUs, and it splits into two parts. There's a fixed always-on charge for
having the agent running at all, and a variable charge for active work, which
covers chats, incidents, scheduled tasks, and triggers. You set the
active-flow allocation yourself and can raise or lower it whenever you want.

My hour of poking at it burned 138 of the 10,000 active-flow AAUs I'd
allocated for the month. Chats accounted for 127 of those and triggers for the
other 11. That's roughly one percent of the allocation for a full repo review
plus a telemetry sweep across five services, which is a useful anchor if
you're trying to guess what a real on-call rotation would run.

## Why this matters if you admin Azure for a living

Cloud admins already know the shape of the problem this addresses: you're
watching more services than you have hours to check by hand, alerts fire
faster than root causes get found, and the person who understands why a
system behaves the way it does is usually one person, not a team. Azure SRE
Agent's pitch is that every investigation it runs builds institutional
knowledge that sticks around even when that one person is on vacation or
moves to another team.

That pitch isn't just theoretical. In
[Rethinking cloud operations with Azure SRE Agent](https://techcommunity.microsoft.com/blog/appsonazureblog/a-paradigm-shift-in-cloud-operations-with-azure-sre-agent/4533244),
Microsoft walked through what happened when three customers actually put it
into production. Zafin took incident triage from hours down to minutes.
Provation Medical had the agent produce analysis for every production-related
ticket in its first month. InEight reported an 80 percent drop in incident
investigation time, an 80 percent drop in build-failure triage time, and a 67
percent drop in bug investigation time. None of those are demo numbers; they're
what happened after the agent was wired into real on-call rotations.

It's not magic, and it's not a reason to stop reviewing what it recommends.
Microsoft is upfront that, like any AI system, it can produce an incorrect
root cause or propose a mitigation that doesn't fit your environment. Treat
its output the way you'd treat a report from a sharp junior engineer: worth
taking seriously, still worth checking before you act on it.

## Go look at what you already have running

If you already have Application Insights collecting telemetry from more than
one service, that's the fastest way to find out whether this is worth your
time. Connect those resources, ask the agent what's unhealthy, and compare
what it says to what you thought was true. An hour is enough to get an answer,
and it's a better hour than the one you'll spend correlating dashboards during
your next on-call rotation.
