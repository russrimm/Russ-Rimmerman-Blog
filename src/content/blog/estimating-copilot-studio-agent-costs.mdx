Estimating Copilot Studio agent costs starts before anyone uses the published agent. If you're building with the GitHub Copilot harness, creating and testing it can consume Copilot Credits too. A harness is the software that coordinates the model's work and the tools an agent uses. A monthly usage estimate covers only part of the work.

I'd use the Copilot Agent Kit's Agent Review Tool to connect that estimate to evidence: inspect activity, validate a change, then budget for rollout. Below, I'll work through that estimate and ways to reduce consumption in both Copilot Studio and GitHub Copilot's coding tools without skipping quality checks.

Billing and savings guidance checked September 15, 2026. The kit workflow follows public documentation and the [September 2026 kit release](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/releases/tag/CopilotAgentKit-September2026), not a recorded walkthrough of a live installation. Agent Review Tool and agent evaluation are preview.

## Know which activities consume credits

The rollout estimate concerns GitHub Copilot harness-based agents built in Copilot Studio. GitHub Copilot's coding tools have separate billing and allowances; don't combine their credits with Copilot Studio's.

Microsoft's [harness usage guidance](https://learn.microsoft.com/en-us/power-platform/admin/manage-usage-github-copilot-harness) says creating, testing, evaluating, and running these agents consumes Copilot Credits regardless of the user's Microsoft 365 Copilot license.

The standard harness, often called Classic in this comparison, has different coverage: qualifying authenticated employee use in Microsoft 365 channels can be included for licensed users, subject to fair use and identity/channel restrictions. Workflows and prompts invoked inside that standard-harness agent by a qualifying licensed user can be covered; other cases are billed. Computer use isn't included. A licensed maker doesn't establish coverage for everyone who uses the agent.

For the GitHub Copilot harness, the [billing overview](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/billing-credit-overview) identifies large language model ("LLM") tokens, tool use, and harness processing as consumption factors. Tokens are pieces of text the model processes or generates. Tools include knowledge retrieval and connections to other services.

There isn't a fixed billed rate per message or task to borrow from standard-harness pricing. Natural-language creation, where you describe changes in everyday language, can consume credits, as can previewing, testing, and generating evaluations. Manual configuration that doesn't use an LLM does not, according to the [September Copilot Credits Guide](https://go.microsoft.com/fwlink/?linkid=2368800).

## Budget the work before rollout

I'd give the project three budget lines before opening the agent builder:

| Phase | Include in the estimate |
| --- | --- |
| Initial creation | Natural-language authoring, previews, and early tests |
| Validation and controlled pilot | Evaluation runs, failed attempts, retries, kit reviews, and pilot usage |
| Ongoing operation | User and autonomous tasks, continued refinement, and repeat validation |

Autonomous tasks start from events or schedules rather than a person asking. Keep those in the forecast even if the expected user count is small.

The initial build is a one-time project allowance. Continued changes belong in the recurring monthly allowance. Power Platform environments are workspaces holding agents, apps, and their data. Choosing a development or trial environment doesn't mean zero consumption under the [current billing rules](https://learn.microsoft.com/en-us/power-platform/admin/manage-usage-github-copilot-harness).

Running the kit's artificial intelligence ("AI")-supported review stages can [consume credits too](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/AGENTREVIEWTOOL_REFERENCE_GUIDE.md), including reruns. Keep an allowance for those outside runtime, meaning the agent doing its users' or scheduled work.

To size the creation allowance, start with a funded, limited building exercise. Compare the agent's reported consumption before and after the exercise once reporting catches up, account for other activity, and use several representative exercises to estimate the remaining work. Don't treat one prompt as a fixed-price unit.

## Reduce Copilot Studio credits before scaling

### Avoid model work where a fixed rule is enough

Make straightforward settings changes manually when they don't need an LLM. Save natural-language authoring for work where it helps you design the agent, rather than repeatedly asking it to rename or adjust something you can edit directly.

For predictable work, compare a standard-harness topic, a defined conversation path, with a response generated by an LLM. Use the [Copilot Credits Guide](https://go.microsoft.com/fwlink/?linkid=2368800) for that harness's billing rules.

### Narrow searches, tool calls, and answers

Give each tool a clear purpose, retrieve only the records and fields the task needs, and avoid repeating the same search when its result is still valid. Use broad enterprise search when the answer needs it, not for a question an approved source can answer. Grounding means using source information to support an answer; keep the sources and permissions that make the response trustworthy.

Ask for the output the user needs: a decision and supporting references, for example, rather than a long report by default. Shorter output can reduce token work in usage-based billing, but doesn't automatically reduce a standard-harness per-response charge.

### Compare complete tasks, not model prices alone

Where model selection is supported, try a lower-cost model on routine work and retain it only if quality holds. More capable reasoning may be worth its cost for harder tasks.

I'd keep the design simple before adding subagents, agents assigned parts of a larger task. Their coordination and repeated instructions can add consumption. Compare the whole task, including retries, before calling the design cheaper.

## Open a live-agent review

Have an administrator follow the kit's [prerequisites](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/PREREQUISITES.md) and [installation instructions](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/INSTALLATION_INSTRUCTIONS.md). Confirm the required Power Apps and Power Automate rights, AI capacity, and connections. Limit reviewers' access to the agents and transcripts, meaning saved conversation records, they need.

Follow the [Agent Review Tool guide](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/AGENTREVIEWTOOL_REFERENCE_GUIDE.md):

1. Open **Setup Wizard**, follow its link to **Copilot Agent Kit Installer**, and select **Set up Agent Review**.
2. Wait for all four setup checks to show **Ready**.
3. In the Makers app, open **Agent Review Tool > Copilot Studio Agents** and select the source environment.
4. Find the agent, select **Review**, and keep the page open until processing and saving finish.
5. Open the saved result, confirm **Powered by: GitHub Copilot**, and select **Cost & efficiency**.

The tool reads the source agent without editing it and saves results in the kit environment. Use a live-agent review; an uploaded agent package has no live transcripts.

## Read the evidence before prioritizing changes

**What did we observe?** uses available transcripts from the last 30 days. Its statuses are **Observed**, **Not observed in the window**, and **Not attributable**. These describe evidence, not spending.

Permissions, retention, and reading limits can leave gaps. “Not attributable” means the evidence doesn't identify an individual capability. Built-in harness actions are excluded, including file reads and commands, the text instructions a computer runs. See the [reference guide](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/AGENTREVIEWTOOL_REFERENCE_GUIDE.md).

Record the window and gaps beside each finding. Call counts aren't tokens, credits, or dollars. For a new agent, collect pilot evidence first; an unobserved capability isn't automatically unused.

## Turn one finding into a testable change

**What should I improve?** connects configuration evidence to recommendations, including overlapping capabilities and unclear tool descriptions. The [September tool](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/releases/tag/CopilotAgentKit-September2026) attaches evidence, a recommendation, quality risk, and a validation plan. It doesn't promise savings.

Suppose a review flags two tools that look like duplicate searches. A connector operation is an action exposed by a connection to another service. Two tools can use the same operation but different connections or business rules, so I'd check those differences before removing either.

If both tools are intentional, a useful first change might be clearer descriptions of when to select each one. I'd test whether that reduces unnecessary searches while preserving access to the correct information.

Save the original settings, record the change and its quality risk, and define success. I'd start with one change so the next evaluation has a clear comparison.

## Validate outcomes and record consumption

In **How do I validate it?**, **Plan one evaluation pass** displays **Consumption varies**. One case can involve multiple interactions and tasks, so case count isn't a test-run price. See the [September release](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/releases/tag/CopilotAgentKit-September2026).

For the overlapping-search example, I'd:

1. Save cases covering each intended search, an ambiguous request, and restricted information.
2. Run those cases before changing descriptions to establish a baseline, a record of current behavior. Use safe test data and only the required permissions. For actions that change records, use connections to an isolated test environment.
3. Make the change in Copilot Studio and rerun the same cases with the same test method and authenticated user profile. Record which agent version each pass tested. Repeat enough to see variation.
4. Check answer quality, expected tool selection, and any actual record changes before comparing consumption.

Copilot Studio's preview [agent evaluation](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-intro) is available through **Evaluate**. Its **General quality** score doesn't compare responses with expected answers. Manually verify required outcomes and restricted-data behavior beyond that score. The review tool doesn't apply changes or execute this validation for you.

During unpublished authoring, use the [Power Platform admin center's Licensing > Copilot Studio reports](https://learn.microsoft.com/en-us/power-platform/admin/manage-copilot-studio-copilot-credits-capacity) for agent and environment totals. Compare matching time windows after reporting catches up, documenting unrelated activity. These aren't per-run or per-user billing reports.

For a useful cost-per-success measure, divide the relevant recorded credits by successful completed tasks. Include credits from failures and retries in the numerator. Keep quality results beside that figure so a cheaper but less reliable change doesn't pass.

## Build a monthly Copilot Studio cost estimate

**How do I plan a budget?** takes **Monthly agent tasks** and a **Runtime scenario**. Include user and autonomous tasks; one conversation can contain several. Don't count every tool call as another task.

The kit's [planning bands](https://github.com/microsoft/Power-CAT-Copilot-Studio-Kit/blob/main/AGENTREVIEWTOOL_REFERENCE_GUIDE.md) are:

| Scenario | Workload assumption | Credits per task |
| --- | --- | --- |
| Light | Few sources, light reasoning, one output at most | 100–300 |
| Medium | Many sources, structured reasoning, multiple outputs | 300–500 |
| Heavy | Broad aggregation, deep reasoning, many outputs | More than 500; no fixed upper bound |

You select the scenario; the tool doesn't infer complexity from transcripts. The estimate is explicitly **Not agent-specific**: identical inputs produce identical estimates. These are planning assumptions, not measured consumption or guaranteed savings. Authoring, testing, and reviews need separate allowances.

Here's an illustrative monthly example for one agent with 500 people granted access but 100 expected active users:

| Planning group | Tasks per month | Selected scenario | Runtime credits |
| --- | --- | --- | --- |
| 80 occasional users | 80 × 5 = 400 | Light | 40,000–120,000 |
| 20 frequent users | 20 × 20 = 400 | Medium | 120,000–200,000 |
| Total | 800 | Combined | 160,000–320,000 |

Assume occasional users want a short answer from a few approved sources. Frequent users want a comparison across several sources plus a written summary. Those task types justify the Light and Medium choices, not frequency or license ownership alone.

These groups are planning assumptions, not individually metered billing categories. Run the Light and Medium portions separately in the kit, then combine them in your own planning worksheet; the kit accepts one scenario at a time.

For this example, add 10,000 credits for monthly natural-language refinement and 5,000 for combined testing, evaluation, and kit reviews. Both are placeholders, not observations or Microsoft recommendations. They're recurring allowances, separate from the initial build budget.

For a smaller pilot or broader rollout, revisit both volume and task complexity.

With a team-selected 20% reserve:

```text
Monthly credits = (runtime credits + 10,000 + 5,000) × 1.20
Low estimate    = (160,000 + 15,000) × 1.20 = 210,000
High estimate   = (320,000 + 15,000) × 1.20 = 402,000
```

Using the [published $0.01 per Copilot Credit](https://go.microsoft.com/fwlink/?linkid=2368800) as a manufacturer's suggested retail price ("MSRP") baseline, runtime alone is $1,600–$3,200. With allowances and reserve, it's **$2,100–$4,020 in United States dollars per month at MSRP**. Those figures give us a common reference, not the customer's contracted price.

**I'd start with pay-as-you-go.** [Link the environment to an Azure billing plan](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/billing-manage-buy-credits) and pay for the credits consumed, rather than purchasing prepaid credit packs and allocating them across environments. That removes the pack-purchasing and allocation work and avoids paying upfront for capacity you might not use. Billing setup, ownership, and usage controls still need attention.

Where the customer's agreement provides applicable discounts, the effective pay-as-you-go rate can be lower than MSRP. Get that rate from the customer's billing or procurement team and substitute it in the forecast; enabling pay-as-you-go doesn't itself guarantee a discount.

```text
Monthly budget = planned Copilot Credits × customer's applicable pay-as-you-go rate
```

Keep the credit forecast and the price assumption separate so a pricing change doesn't require rebuilding the usage estimate. If the organization already has prepaid commitments, account for those when comparing incremental cash spend.

The reserve isn't a spending cap, and this finite range doesn't bound Heavy tasks. Add event-driven work separately if applicable, then replace assumptions with pilot evidence. Repeat this method per agent before combining budgets. Budget external services, storage, and reviewer labor separately under their own terms without counting the same credits twice.

## Reduce GitHub Copilot tokens and AI credits separately

[GitHub AI Credits](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing) measure GitHub Copilot's model usage, not Copilot Studio consumption. Input is what the model receives; output is what it generates. Cached tokens come from information stored for reuse. Each has [model-specific prices](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing). Business and Enterprise allowances are pooled under the paying account; personal plans have their own allowances.

### Give the task boundaries and a stopping point

Name the relevant files, expected outcome, and checks to run. Use a question-only interaction for an explanation, and an agent to change files and run commands. More steps can cost more, but there's no fixed price ratio between modes.

For a coding task, I might ask:

```text
Fix the date display in the named file. Preserve existing behavior elsewhere.
Run the project's existing checks for this change. Stop when they pass.
Report the change and any remaining risks briefly; don't repeat the full file.
```

Concise output saves generated tokens; it isn't permission to skip reasoning, security checks, or necessary explanations. On paid plans, code completions and next edit suggestions, the suggestions shown as you type or edit, aren't billed in AI credits. Use those when a small suggestion is all you need.

### Carry forward useful context, not everything

Context is the instructions, history, files, and tool results supplied to the model. Keep related follow-ups in one session, or conversation; [start fresh when the problem changes](https://docs.github.com/en/copilot/tutorials/optimize-chat-usage). After a large investigation, carry a short plan with file locations, decisions, and required checks into the session where you'll make changes.

In GitHub Copilot's command-line interface ("CLI"), where you work by typing commands, `/new` or `/clear` starts fresh. Use `/compact` to summarize a long session you need to continue, and `/context` to inspect its size. Compaction can lose detail, so preserve important decisions.

Keep `.github/copilot-instructions.md` or `AGENTS.md`, files containing standing project instructions, short and specific. Include the project map, known pitfalls, and check commands. Remove repeated prose, not safety rules. Disabling unneeded Model Context Protocol ("MCP") tools, which connect Copilot to other services, also reduces context. Do that before starting the task.

Prefer concise command output over pages of passing results, but retain failures and warnings. For GitHub's cloud agent, which works in a GitHub-hosted environment, [preconfigure setup](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment) in `.github/workflows/copilot-setup-steps.yml`. Installing required tools and software there avoids repeated setup guesswork; GitHub Actions execution has its own billing rules.

### Match the model and preserve reusable context

For routine work, try a lower-cost model or **Auto**. GitHub documents a [10% model-cost discount for paid plans using Auto](https://docs.github.com/en/copilot/concepts/auto-model-selection) in supported Copilot experiences. That isn't a 10% discount on your entire subscription or a Copilot Studio benefit.

Where supported, leave reasoning at the regular level unless the task needs more. A cheaper model that needs repeated corrections may cost more per successful change.

A prompt cache stores reusable context. Cached input can cost less, but rates and cache-write charges vary by model. Avoid switching models, reasoning settings, or tool sets unnecessarily mid-task; those changes can invalidate the cache. GitHub's [efficiency guide](https://docs.github.com/en/copilot/tutorials/optimize-ai-usage) covers these tradeoffs.

### Watch usage and limit open-ended work

Review GitHub's **AI usage** page by feature and model. For Business and Enterprise, additional paid usage is enabled by default; have the administrator review that policy and configure user budgets and organization or enterprise spending limits.

The CLI's preview [session limit](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit) can pause a long task. For example, `/limits set max-ai-credits 100` sets a 100-credit allowance for that session. It's a soft limit: an in-progress response can finish and exceed it. It doesn't replace monthly controls.

## Hand off the budget with rollout controls

Publish to a controlled pilot before broad rollout. The agent's [Monitor experience](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-overview) becomes available only after publishing and shows credits, sessions, and tool use; data can lag by up to an hour. Use it alongside admin-center reports, which distinguish billed and nonbilled consumption. For pay-as-you-go monetary charges, reconcile with Azure Cost Management after reporting delays.

Before expanding access, confirm the billing plan and applicable per-credit rate. Name the person who reviews consumption, the owner who approves a higher budget or usage limit, and who responds if the agent stops. Record the accepted quality checks and the next forecast review date.

In the admin center, [Licensing > Copilot Studio > Manage Agents > Set limit](https://learn.microsoft.com/en-us/power-platform/admin/manage-usage-github-copilot-harness) provides the agent limit, notification threshold, and **Stop usage** control. Agree on those settings with the service owner, including for development and test agents. Separate environments make usage easier to track, but an allocation alone isn't a cap if it can draw from the organization's shared credit pool or pay-as-you-go. Azure budget alerts aren't hard stops.

I'd begin with one agent and one representative task set. Validate one cost-saving change, compare credits per successful task, and revise the forecast. Apply the same discipline to GitHub Copilot work, but keep its usage and budget separate.
